# Global Drop Trade v0.7.0

This release updates the smart-contract seller plan and capped multi-branch reward aggregation, replaces the requested landing-page icons with responsive concept imagery, includes all 18 supplied FAQ answers, and adds a read-only API for confirmed `SaleSettled` events.

## Contract behavior

- Seller tier rates, from direct parent to level four: `8/4/2/0`, `10/5/3/0`, `12/6/4/0`, `14/7/5/0`, `16/8/6/4` percent. Rates still apply to funded gross sales profit, using the seller's tier. The existing active/VIP/KYC rules for recipients remain.
- Each independent branch contributes at most 60%, 45%, or 35% of the goal. All branches can contribute to rank qualification; reward groups can grow beyond three branches, using batches of at most 64 additions.
- Reward percentages across the 14 goals are 7% through $10k, 6% through $100k, 5% through $1m, and 3% thereafter.
- Existing sequential **additional-volume consumption** is preserved. Rank historical volume remains independent. Reward preparation reserves volume for the current stage, and failed payouts cannot erase that entitlement or advance the stage.
- Large groups use `prepareNetworkReward(group, steps)` repeatedly, then `claimNetworkReward(group)`. A failed claim reverts its own changes but preserves successful preparations from earlier transactions.
- The old `createRewardGroup(address[3])` signature and `largestBranches` getter are replaced. Use the committed current ABI and `networkBranchCount`, `networkBranch`, `rankVolumePage`, `rewardProgress`, and `rewardBranch`.
- The deployed old contract is immutable. These code changes require a **new contract deployment** to affect on-chain behavior. This update does not migrate funds/users or send a deployment transaction. Never delete old deployment journals to force a new deployment.

The exact schedule and preserved economic rules are in `NETWORK-PLAN.en.md`.

## Read-only transaction API

`GET /api/trades?limit=12` returns **confirmed contract sales settlements** with exact amount strings, timestamps, transaction hashes and explorer links. It is not a marketplace order API, execution bot, proof of off-chain commerce, or net-profit feed. `grossProfit` is the funded gross settlement amount; `salesUsd` is the authorized reporter's claimed sales volume. Records are bounded to the configured recent block window and at most 100 newest records.

The service requires only RPC read access. No wallet, private key, or transaction signing is used. It validates chain ID, contract code, contract token metadata, asset type, confirmation depth and block hashes. Duplicate/removed logs are excluded. Public polling is cached and concurrent requests share one RPC refresh. Outages label the previous snapshot stale; an unconfigured/unavailable source never generates example trades. BNB testnet records are clearly marked.

### Installation on the existing Ubuntu host

For an existing server, `sudo bash ubuntu-connect.sh /root/global-bnb` runs the complete read-only connection flow **from a separate checkout of this release**. The argument points to the existing project; its source files, keys and deployment journals are not changed. The installer:

- Reuses an active API target, otherwise the existing website's public target or one unambiguous deployment-public report. It does not assume mainnet when the target is missing. Conflicting testnet/mainnet reports require explicit selection.
- Reads a configured RPC from the API environment or the existing server's network-specific environment. Missing chain/address/RPC settings are requested interactively on the server. The RPC must support `eth_getLogs`; no public endpoint is silently selected.
- Verifies a live read-only feed and records whether all five referral schedules, all fourteen rewards and the three per-line caps match this release. A legacy contract can supply the feed, but is explicitly reported with `requestedPlanChecksMatch: false`.
- Builds the website with the verified public chain/address, installs the API with private credentials kept server-side, preserves previous environment settings on API activation failure, then installs the website through the existing SSL-preserving installer.
- Checks the HTTPS virtual host and connected API before printing `HTTPS_SITE_AND_READ_ONLY_FEED_CONNECTED`. The public connection report is `/etc/globaldroptrade/connection-public.json`; private backup environment files remain under `/etc/globaldroptrade/backups/` with restricted permissions.

This path requires root, Nginx with the existing HTTPS certificate, Python 3, curl, systemd and Node.js 20.19+ or 22.12+ with npm. It can copy the older Global install's bundled Node v22.23.3 from its `.runtime` directory to a service-readable `/opt` directory when needed. It does not install Node from an unverified download. Run interactively in the server terminal so missing connection details can be entered there; never paste private RPC credentials or wallet keys into chat.

No blockchain transaction, new deployment, fund migration or marketplace-order connection is performed by this installer. A successful feed connection does not update an old immutable contract. Existing deployment scripts and their review requirements remain separate.

First update the repository to the reviewed release commit using a clean checkout. Preserve local environment files and deployment journals. Node.js 20.6+ must be installed in a system-readable path, together with npm, Nginx, curl and systemd.

```bash
cd /root/global-bnb
sudo bash ubuntu-api.sh
sudo bash ubuntu-website.sh
curl -fsS http://127.0.0.1:3115/api/health
sudo systemctl status globaldroptrade-api --no-pager
```

`ubuntu-api.sh` creates `/etc/globaldroptrade/trades.env` only if absent, preserves its content on updates, runs the service as an unprivileged system user, and restores the previous service on startup failure. The website installer preserves the existing HTTPS configuration and adds the `/api/` proxy to localhost:3115. Its existing Nginx rollback applies to the new API snippet too. The website and API can be installed before connecting a contract; the feed then explicitly says it is not connected.

Edit `/etc/globaldroptrade/trades.env` **on the server** with the verified contract address, matching chain ID and your RPC URL. Do not share RPC credentials in chat or commit this file. Use 97 for testnet or 56 for mainnet, and optionally the verified deployment block. Existing reports can provide the address, but a report from an old contract does not make that contract run the new rules.

```bash
sudo nano /etc/globaldroptrade/trades.env
sudo systemctl restart globaldroptrade-api
curl -fsS 'http://127.0.0.1:3115/api/trades?limit=3'
```

The optional dashboard wallet target is configured separately through the existing public `website/.env` settings (`VITE_CHAIN_ID`, `VITE_VAULT_ADDRESS`) and requires a website rebuild/package. The read-only public feed does not change the wallet transaction target.

Actual marketplace orders require that marketplace's authorized API connection, which has not been supplied. No public-chain RPC/contract activation or production-server deployment is claimed by this package.
